Tax Payment Portal / TTR Automation

PySpark, Airflow, Kafka, Snowflake, SQL, AWS
1
How did you handle 10M+ records and partitioning in PySpark?
When we have lots of data (like 10 million rows), we can't process it all at once - it's like trying to eat a whole pizza in one bite! So we break it into smaller pieces called partitions.

Date-based Partitioning: I split data by date (like January data in one folder, February in another). This way, when someone asks for January data, we only look at that small piece, not everything.

Handling Skewed Data: For skewed data (when some days have way more invoices than others), I used salting - I added a random number to the busy partitions to spread the work evenly across all computers.

💡 Think of it like having 10 cashiers at a store - you don't want all customers going to one cashier!
2
How did you handle Kafka exactly-once delivery?
Imagine sending a WhatsApp message - you want it delivered exactly once, not zero times (lost) or twice (duplicate).

Idempotent Producer: I used Kafka's idempotent producer - this means even if we accidentally send the same message twice, Kafka is smart enough to keep only one copy.

Consumer Rebalancing: For consumer rebalancing (when we add or remove computers), I used manual offset commits - I only mark a message as 'done' AFTER I've successfully saved it to the database.

✅ This way, if something crashes, we just re-read the last few messages and try again.
3
Why did you use views instead of materialized views?

View: Like a window - every time you look through it, you see what's happening right now (live data).

Materialized View: Like taking a photo - it's faster to look at, but it shows old information until you take a new photo.

📊 I chose regular views because our tax data changes frequently during the day, and users always need the latest numbers. The query was fast enough (under 3 seconds) so we didn't need to 'take photos' and refresh them.

Clustering Keys: I used (business_unit, fiscal_year) because most queries filter by these columns - it's like organizing books by genre and year so you can find them faster.

4
How did you handle schema evolution in Parquet?

Schema evolution means when the source team adds new columns to their data without telling us!

It's like having a flexible form - if someone adds a new field, we just add a new box on our form instead of throwing an error.

I used PySpark's mergeSchema=true option:

df = spark.read.option("mergeSchema", "true").parquet("path/")

For old data that doesn't have the new column, we just fill it with null (empty). This way, our pipeline never breaks when sources add new fields.

5
How did you handle BU/Sub-BU hierarchy?

Our company has a tree structure - like a family tree: Main company → Business Units → Sub-Business Units → Teams

I used a recursive CTE (a query that calls itself) to walk through this tree:

WITH RECURSIVE hierarchy AS ( SELECT id, parent_id, name, 1 as level FROM orgs WHERE parent_id IS NULL UNION ALL SELECT o.id, o.parent_id, o.name, h.level + 1 FROM orgs o JOIN hierarchy h ON o.parent_id = h.id ) SELECT * FROM hierarchy;
⚠️ Our hierarchy was 5 levels deep. For circular references (A reports to B, B reports to A - which is wrong), I added a check: if we go more than 10 levels deep, stop and flag it as an error.

EID Identification & Mapping Dashboard

PySpark, Airflow, Snowflake, SQL, Sigma
7
How did you handle different formats from Big 4 firms?

Each firm (Deloitte, EY, KPMG, PwC) sends data in different formats - like four people writing their addresses differently.

I created a mapping configuration file for each firm:

mappings = { 'deloitte': {'emp_id': 'EID', 'emp_name': 'EmployeeName'}, 'ey': {'employee_id': 'EID', 'name': 'EmployeeName'}, ... }

15-20 edge cases handled:

  • Date formats (MM/DD/YYYY vs DD-MM-YYYY)
  • Number formats (1,000.00 vs 1.000,00)
  • Missing optional fields

I handled these with a cleaning function that standardizes everything before loading.

8
How did you implement incremental loading?

Incremental loading means: don't reload ALL data every time, just load NEW or CHANGED data.

I used Snowflake MERGE statements:

MERGE INTO target_table t USING source_table s ON t.eid = s.eid WHEN MATCHED THEN UPDATE SET ... WHEN NOT MATCHED THEN INSERT ...

Watermark tracking: I tracked the last_modified_date. Each run, I only pick records where modified_date > last_watermark.

🔄 For late-arriving data, I keep a 3-day lookback window - we always reprocess the last 3 days just in case.
9
How did you deduplicate EIDs?

Deduplication means removing duplicate records of the same person.

Deterministic matching - exact matches on:

  • Employee ID
  • SSN (last 4 digits)
  • Date of Birth
✅ If all three match = same person (100% confident)

Fuzzy matching (when names are spelled slightly different):

  • First name + Last name similarity (Levenshtein distance)
  • If similarity > 85% AND same DOB = probably same person

Our false positive rate was about 2% - meaning 2 out of 100 matches might be wrong. We flagged these for human review instead of auto-merging.

10
How did you handle Time Travel for audits?

Snowflake Time Travel is like a time machine for data - you can see what the data looked like yesterday, last week, etc.

Our retention period was 14 days (Snowflake Enterprise default). We could go back 14 days to see old data.

💰 For storage costs: longer retention = more storage = more money. 14 days was a good balance because most audit questions are about recent changes.

For older history, we saved daily snapshots to a separate archive table (cheaper storage). If we needed data older than 14 days, we queried our archive table instead.

11
How did you implement CDC (Change Data Capture)?

CDC means capturing only the changes (inserts, updates, deletes) instead of reloading everything.

I used Snowflake Streams:

CREATE STREAM eid_changes ON TABLE eid_master;
A stream is like a camera watching a table - it records every change.

For offset tracking, Snowflake handles this automatically. After we process the changes, we consume the stream (like marking emails as read).

For transactional consistency across multiple tables:

BEGIN TRANSACTION; -- process stream 1 -- process stream 2 COMMIT;

Either all tables update, or none do.

12
How did you build the unmapped EID flagging logic?

Our rule engine was rule-based (not ML) - simple IF-THEN rules:

Rule 1: IF eid NOT IN master_list → FLAG as 'Unknown EID' Rule 2: IF eid IN master_list BUT department IS NULL → FLAG as 'Missing Department' Rule 3: IF eid status = 'Terminated' BUT has new transactions → FLAG as 'Suspicious Activity'

I stored these rules in a config table so business users could add new rules without changing code.

Decision flow:

  1. Check if EID exists → No? Flag it
  2. Check if all required fields present → No? Flag it
  3. Check if EID is active → No? Flag it
  4. All checks pass → Mark as 'Valid'

Tax Data Exchange (DEX) Dashboard

PySpark, SQL, Airflow, Snowflake, Sigma
13
How did you handle DEX vs TRACK reconciliation?

Reconciliation means checking if two systems have the same numbers.

Our tolerance threshold was $0.01 (one cent) - if the difference is less than 1 cent, we consider it a match. This handles floating-point precision issues.

System Amount Difference Result
DEX $1000.001 $0.001 ✅ MATCH
TRACK $1000.00

For larger differences, we flagged them for review. I used ROUND() function in SQL to ensure consistent decimal places before comparing.

14
What changed when you moved from Tableau to Sigma?

Tableau uses extracts - it downloads data once and queries the local copy (fast but stale).

Sigma uses live queries - it asks Snowflake directly every time (always fresh but slower).

Changes I made:

  1. Created summary tables in Snowflake (pre-aggregated data) so Sigma queries are fast
  2. Added caching at the Snowflake layer using result caching
  3. Simplified complex calculations - moved them from dashboard to SQL views
✅ Result: Dashboard loads in 3-5 seconds (acceptable) and data is always live.
15
How did you implement version comparison (SCD)?

SCD Type 2 means we keep full history of every change.

When a tax record changes:

  1. Mark old record as is_current = FALSE, set end_date = today
  2. Insert new record with is_current = TRUE, start_date = today, end_date = NULL
EID Amount start_date end_date is_current
123 $1000 2024-01-01 2024-06-01 FALSE
123 $1200 2024-06-01 NULL TRUE

For change flags, I added columns like amount_changed (TRUE/FALSE) and amount_delta ($200 in above example).

16
How did you handle K1/K3 IRS schema validation?

Schedule K-1 is a tax form with very specific fields required by IRS.

I built validation rules based on IRS Publication 541 requirements:

  1. Partner's SSN or EIN must be valid format
  2. Box 1-20 must have correct data types (numbers, not text)
  3. 199A fields (Box 20, Code Z) must match specific calculations
  4. 8886 footnotes must be present if certain transaction types exist

~30+ edge cases handled:

  • Negative income scenarios
  • Multi-state allocations
  • Foreign partner withholding
  • Guaranteed payments calculations

Each rule was coded as a SQL check, and failures were logged with specific error messages for the tax team to fix.

17
How did you handle concurrent edit conflicts?

When two people edit the same thing at the same time, someone's work might get lost!

I used optimistic locking:

  1. When User A opens a record, we note the version_number = 5
  2. When User A saves, we check: is version still 5?
    • Yes → Save and make version = 6
    • No → Someone else changed it! Show error: 'Please refresh and try again'
UPDATE hierarchy SET name = 'New Name', version = version + 1 WHERE id = 123 AND version = 5; -- Only works if version unchanged

If zero rows updated, we know there was a conflict and alert the user.

18
How did you differentiate amended returns from duplicates?

Our composite key for identifying unique records was: Entity ID + Tax Year + Form Type + Version Number

Amended returns have a higher version number:

  • Original: Entity=123, Year=2024, Form=K1, Version=1
  • Amended: Entity=123, Year=2024, Form=K1, Version=2 ← This is intentional!

True duplicates have same version:

  • Record 1: Entity=123, Year=2024, Form=K1, Version=1
  • Record 2: Entity=123, Year=2024, Form=K1, Version=1 ← This is an error!
📋 Rule: Same key with DIFFERENT version = Amendment (keep both) | Same key with SAME version = Duplicate (flag for review)

Architecture & Infrastructure Deep Dives

Testing, AWS, CI/CD, Performance, Cost Optimization
19
How did you test Airflow DAGs?

Testing Airflow DAGs has 3 levels:

1. Unit Tests - Test individual functions:

def test_transform_function(): input_data = [...] result = transform(input_data) assert result == expected_output

2. DAG Validation Tests - Check DAG structure:

def test_dag_loads(): dag = DagBag().get_dag('my_dag') assert dag is not None assert len(dag.tasks) == 5

3. Integration Tests - Run with sample data in test environment

🔄 For idempotency (running twice gives same result), I tested by running pipeline once → Check results → Running again with same data → Results should be identical. If record counts doubled, something is wrong!
20
Give 3 specific Great Expectations rules you wrote:

1. No null values in required fields:

expect_column_values_to_not_be_null(column='eid')

2. Amount should be positive:

expect_column_values_to_be_between( column='tax_amount', min_value=0, max_value=1000000000 )

3. Date format should be valid:

expect_column_values_to_match_regex( column='fiscal_date', regex=r'\d{4}-\d{2}-\d{2}' # YYYY-MM-DD format )

For expectation drift (when rules become outdated), I reviewed and updated expectations every quarter with the data team.

21
How did you configure EMR and handle spot instances?

Our EMR cluster configuration:

  • Master node: m5.xlarge (reliable, on-demand)
  • Core nodes: r5.2xlarge (memory-heavy for Spark)
  • Task nodes: r5.2xlarge SPOT instances (cheap but can disappear)

I chose r5 (memory-optimized) because PySpark loves RAM for caching data.

Spot termination handling:

  1. Enabled checkpointing - Spark saves progress every 10 minutes
  2. If spot instance dies, another takes over and resumes from checkpoint
  3. Critical jobs used on-demand only (no risk)
  4. Non-critical jobs used 70% spot + 30% on-demand mix
💰 This saved us about 60% on compute costs compared to all on-demand.
22
How did you handle REST API failures with Appian?

Retry logic:

@retry(tries=3, delay=5, backoff=2) # 3 tries, wait 5s, then 10s, then 20s def call_appian_api(data): response = requests.post(url, json=data) response.raise_for_status() return response

Circuit breaker (stop trying if API is totally down):

  • If 5 failures in 1 minute → Open circuit (stop calling)
  • Wait 5 minutes → Try one test call
  • If test works → Close circuit (resume normal calls)

For partial batch failures (some records succeed, some fail):

  • I logged failed records to a 'dead letter queue' (separate table)
  • A separate job retried these failed records every hour
  • After 3 retries, alert the team for manual intervention
23
What was your actual latency SLA?

Our SLA was 'near real-time' which meant: Payment events visible in dashboard within 5 minutes of occurring.

It was actually micro-batch, not true streaming:

  • Kafka consumers ran every 30 seconds
  • Processing took ~2 minutes
  • Dashboard refresh every ~2 minutes
  • Total end-to-end: ~5 minutes
⚠️ Kafka consumer lag tolerance: Maximum 10,000 messages behind. If lag exceeded this, PagerDuty alert fired and we investigated.

For truly time-sensitive alerts (like fraud detection), we had a separate true streaming pipeline with <10 second latency.

Give an example of conflicting stakeholder requirements:

Real example:

🔬 Data Scientist wanted: Raw, granular transaction-level data (millions of rows) for ML model training.

📊 Business Analyst wanted: Aggregated daily summaries (thousands of rows) for quick dashboard loading.

⚡ Conflict: One wanted big data, other wanted small data from the same source.

How I resolved it:

  1. I created TWO data products from same pipeline:
    • transactions_raw table → For Data Scientist
    • transactions_daily_summary view → For Business Analyst
  2. Both fed from same source, maintained by same pipeline
  3. Everyone happy! Data Scientist got details, BA got speed
💡 Key learning: Don't choose one over other - find solution that serves both.

What was the AWS spend and cost optimization you did?

I managed approximately $15,000-20,000/month in AWS spending for our data infrastructure.

Specific cost optimization:

⚠️ Problem: Our EMR cluster ran 24/7 but jobs only ran 6 hours/day.

Solution:

  1. Changed from persistent cluster to transient clusters (start → run job → terminate)
  2. Used spot instances for task nodes
  3. Scheduled clusters with Airflow (only spin up when needed)
Metric Before After Savings
EMR Monthly Cost $8,000 $3,200 $4,800 (60%)
💰 Another win: Moved cold data (>90 days old) from S3 Standard to S3 Glacier. Saved additional $500/month on storage.
